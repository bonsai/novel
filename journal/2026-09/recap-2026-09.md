```text

  ↓

  ↓
```

同時に「糸とAI」という小説制作を進め、AIを単なる文章生成器ではなく、設計・制作・記録を支える相棒として扱う方向が生まれた。

# 5. 2026-09-08 — ChatGPT全セッションrecapという発想の確立

## 既存recapの確認

`journal/2026-09/`には、それまでに以下の3ファイルが存在していた。

- `recap-2026-09-01-08.md`
- `recap-2026-09-08.md`
- `recap-2026-09-08-hanashi.md`

3つはそれぞれ、月初からの活動recap、当日の詳細recap、小説風recapという異なる形式だった。

今回、それらを一つの総合recapへ統合する方針とした。

## 重要な方向転換

当初はGitHubの活動履歴をjournalにまとめることが中心だったが、会話を進める中で目的を明確化。

**本当に残したいのはGitHubの履歴ではなく、ChatGPTとのセッションそのもの。**

つまり、記録するのは「何をcommitしたか」だけではなく、

- 何について話したか
- 何を考えたか
- 何に迷ったか
- 何を決定したか
- 何を作ったか
- 何が失敗したか
- 何を次にやることにしたか
- 次のセッションへ何を引き継いだか

である。

## 3時間単位journal

活動を3時間単位にまとめる考え方を確定。

```text
ChatGPT sessions
      ↓
session recap
      ↓
3時間単位に集約
      ↓
┌──────────────┐
│ work         │
│ decisions    │
│ ideas        │
│ GitHub       │
│ failures     │
│ next tasks   │
└──────────────┘
      ↓
novel/journal
      ↓
daily
      ↓
weekly history
```

時刻が確認できないセッションについては、無理に3時間へ割り当てず、日単位で保持する方針。

## Issue #1

`bonsai/novel`に以下の設計Issueを作成。

**設計: ChatGPT全セッションrecap → 3時間単位journal統合**

設計の中心は、ChatGPT全セッション→session recap→3時間集約→daily/weekly historyという流れ。

また、ChatGPTの過去セッション本文をGitHubから直接取得できると仮定しないことも明記した。

利用可能なrecap / export / API等を入力ソースとし、存在しない会話内容は推測しない。

## 自動化について

現在のリマインダーは日次。

標準Automationだけでは3時間ごとの実行をそのまま設定できないため、3時間集約処理そのものはGitHub Actions等のWorkflow側で実装する余地がある。

リマインダーとrecap生成処理を分離する方向。

# 7. 9月に生まれた主要な概念

## repo2agent

repoを読めばAgentが生まれる、という発想。

```text
repo
→ README
→ structure
→ YAML
→ Ontology
→ Agent
→ Workflow
```

## GitHub = Evidence center

GitHubは単なるコード置き場ではなく、設計・実装・決定・成果を結びつけるEvidenceの中心。

ただし、ChatGPTの思考そのものはGitHub commitだけでは残らないため、recapを別のEvidenceとして保存する。

## ChatGPT recap = 思考Evidence

ChatGPTとの会話には、commitには残らない「なぜそうしたか」が含まれる。

そのため、

```text
GitHub commit = 実装Evidence
ChatGPT recap = 思考Evidence
Issue         = 設計Evidence
journal       = 活動史
```

という役割分担が成立した。

## journal = History

journalは単なるログではなく、未来の自分やAgentが過去を理解するためのHistoryとして設計する。
